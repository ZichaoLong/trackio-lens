# 开发规范

本文是本仓库开发方式的规范源。目标是快速定位、有限阅读、明确事实来源和可靠接续，不设文件行数目标。
产品行为见 [产品约定](product.md)，任务进展见 [当前状态](status.md)。

## 导航与读取

从当前任务、Git 状态和相关约定开始，定位公开入口、负责实现的模块及对应测试。
应用代码形成后维护 `docs/architecture.md`，用真实路径和符号将常见任务连接到这些位置；
导航只保存引用与必要的职责说明，不重复维护默认值、行为规则或完整调用图。

先用文件名、符号、路由或配置键缩小搜索范围。只有直接调用、共享状态、接口消费者
或失败测试指向相邻模块时才扩大读取；足以判断行为、修改位置与验证方式后停止扩读。
导航缺失或过时时从实现和约定重新定位，修正本次相关引用，不用过时索引裁决行为。

代码本身也应容易导航：命名体现职责，接口和依赖显式，经常一起变化的逻辑集中维护。
关键模块应能看出输入输出、状态归属和副作用。小改动反复需要通读无关代码时，改善边界；
不靠大量转发层或必须一起阅读的碎片文件降低表面文件大小。上游导入结构按实际需要渐进调整。

## 事实来源

| 事实 | 来源与维护方式 |
| --- | --- |
| 产品目标和行为约定 | `docs/product.md`；重要取舍按需记录到 `docs/decisions/` |
| 当前实现、配置默认值、接口定义和可变状态 | 对应的实现、schema 或配置入口；一个事实有明确的维护位置 |
| 上游来源与依赖版本 | 导入时建立的机器可读版本记录、锁文件；重复字段应生成或校验一致性 |
| 验证结果 | 与源码提交对应的检查结果；测试通过只证明其实际覆盖的行为 |
| 开发进度与下一步 | `docs/status.md`，链接必要证据，不复制整段日志 |
| 实际部署版本与健康状态 | 对运行实例的检查和部署记录，不能从 Git HEAD 或进度文档推断 |

计划、已实现、已验证、已发布和已部署分别记录。代码与约定不一致时查清并修正，
不能把当前实现自动当作正确约定，也不能把文档描述当作执行证据。
其他文档引用事实源，避免多处手写同一配置或版本。

## 修改与验证

编辑前明确涉及的约定、实现、直接消费者及验证入口，使用局部补丁。
行为改变时同步相关约定和测试；路径、职责或测试入口改变时，同次改动修正导航。
重要设计取舍记录原因与影响，不为每次小改动创建文档。

检查命令以项目实际脚本和配置为准。先验证受影响行为，再运行该改动需要的 lint、构建
和更广检查。缺少工具或环境应单独说明；未执行的检查不能记为通过。
认证、数据兼容和部署需要边界行为验证；界面检查区分模拟视口与真机结果。
推送后如存在相关 CI，核对对应提交的实际结果，本地通过不代表远端 CI 通过。

## 提交、交付与接续

一个可验证的逻辑变化形成提交，附相关测试和必要文档；原样导入上游作为独立基线，
纯结构调整与行为修改尽量分开。审查实际差异，只暂存本次负责的内容；修正已推送内容优先追加提交。

按当前任务已有授权执行推送和部署。一个可运行阶段可包含多个提交，部署从已提交代码构建；
文档或测试独立修改不需要重启应用。具体实例地址和凭据不属于通用规范。

阶段结束或线程交接时更新 `docs/status.md`：已完成内容、相关提交、检查结果、未验证部分、
下一步及所需入口。本机运维明细、秘密和原始运行日志保存在仓库外；公开状态只保留可公开信息。
接续时重新核对 Git 状态与相关事实源，历史记录不自动授权新任务。

用调整会话有效期、修改图表布局、升级 Trackio 等实际任务检查导航：能否找到事实源、
实现、影响范围和验证命令。先维护简单链接和可执行检查，只有真实重复工作证明有价值时
才增加索引或辅助脚本；不把文件数、行数或文档数当作质量指标。
